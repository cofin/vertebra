# 1.1 QueueBackend protocol, MemoryQueueBackend, and ValkeyQueueBackend / RedisQueueBackend

## Objective
Extract the `QueueBackend` protocol, `MemoryQueueBackend`, `DeadLetterEntry`, `CronLease`, and enriched `TaskEnvelope` / `QueueConfig` into `src/py/vertebra/framework/queues/base.py`, implement `RedisQueueBackend` and `ValkeyQueueBackend` in `src/py/vertebra/framework/queues/redis.py` over Redis/Valkey Streams (`XREADGROUP`, `XACK`, `XAUTOCLAIM`), sorted-set delayed scheduling (`ZADD` + atomic Lua promotion), and dead-letter streams (`<prefix>:dlq`), and wire URL-scheme backend construction (`memory://`, `redis://`, `rediss://`, `valkey://`, `valkeys://`) in `QueueService`.

## Context
- `framework-consolidation:5.7` flattened `queues` into single-file module `src/py/vertebra/framework/queues.py`. Promoting `queues` into a multi-backend subpackage requires removing `src/py/vertebra/framework/queues.py` via `git rm src/py/vertebra/framework/queues.py` before creating `src/py/vertebra/framework/queues/__init__.py`, `base.py`, and `redis.py`. Keep worker lane orchestration consolidated in `src/py/vertebra/server/lanes.py`.
- `TaskEnvelope` currently stores only `(task_id, task_name, lane, args, kwargs, attempt)`, and `QueueService` appends to a plain `list[TaskEnvelope]` regardless of `QueueConfig.backend_url` (finding `FW-07`).
- Distributed at-least-once task queues require:
  1. Visibility timeout tracking so an unacknowledged message from a crashed consumer is reclaimed after `visibility_timeout_seconds` via `XAUTOCLAIM`.
  2. Delayed/scheduled task promotion (`enqueue(..., delay_seconds=...)` or `scheduled_at=...`) stored in a ZSET (`<prefix>:scheduled`) and atomically promoted into the target lane stream (`<prefix>:lane:<lane>`) via a Lua script (`EVALSHA` / `EVAL`) per Decision D1.
  3. Dead-letter routing: when `attempt >= retry_policy.max_retries` and a task fails (or `nack(..., requeue=False)` is called), the failed envelope and error traceback summary are written to `<prefix>:dlq` (`XADD <prefix>:dlq MAXLEN ~ <dlq_max_len> * ...`) and acknowledged on the source lane stream (`XACK`).
  4. Distributed lease acquisition (`SET <lease_key> <owner_id>:<slot> NX PX <ttl_ms>`) and conditional renewal/release via Lua for `CronScheduler` leader election.
- `behavior_tdd` applies because `QueueBackend`, `MemoryQueueBackend`, `RedisQueueBackend`, and `ValkeyQueueBackend` introduce new observable distributed queue capabilities.

  - Implement atomic Lua script `_PROMOTE_SCHEDULED_LUA` (Decision D1): queries `ZRANGEBYSCORE KEYS[1] '-inf' ARGV[1] LIMIT 0 ARGV[2]`, decodes target stream key per item, calls `XADD`, and removes promoted members with `ZREM`.
