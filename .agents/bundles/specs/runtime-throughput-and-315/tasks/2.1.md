# Task 2.1: Eliminate BatchBridge deadlock and add zero-copy in-process batch snapshot and direct response callback

## Objective

Eliminate the `BatchBridge` bounded-channel deadlock in embedded mode (`c >= 16` on 1 core, `c >= 32` on 8 cores), replace `BridgeResponse`'s `Vec<(Vec<u8>, Vec<u8>)>` header vector with zero-copy `headers_raw: Bytes`, add a direct Rust response completion callback bypassing intermediate channel hops, and add zero-copy `BatchSnapshot::from_inprocess` so embedded requests never copy through a `1 MiB` `DataSlab` or drop with `SlabFull`.

## Context

In `src/rs/vertebra-core/src/bridge.rs`:
- `batch_tx` is `crossbeam_channel::bounded(4)` and `resp_tx` is `tokio::sync::mpsc::channel(4)`. Synchronous `batch_tx.send(snap)` inside async Tokio tasks blocks every Tokio worker thread while the Python thread blocks in `resp_tx.blocking_send(resp)`, causing deterministic ABBA deadlock whenever `> 5` batches are in flight (`c >= 16` on 1 core, `c >= 32` on 8 cores, or async `io10`).
- `BatchWriter` acquires a global `Mutex<()>` (`write_lock`) and copies request strings and bodies into a fixed `1 MiB` `DataSlab`, dropping requests (`503`) if a batch exceeds `1 MiB`.
- `BridgeResponse` stores `headers: Vec<(Vec<u8>, Vec<u8>)>`, forcing `InProcessTransport::submit_response_raw` to decode compact binary headers into heap `Vec`s only for `vertebra-http` to iterate them again.

## Steps

1. Add a reproduction unit test in `src/rs/vertebra-core/src/bridge.rs` that pushes `64` batches into `BatchBridge` before draining responses from a single consumer thread, proving the bounded-channel ABBA deadlock or stall cannot occur, plus a test verifying zero-copy `InProcessRequest` batches exceeding `1 MiB` succeed without `SlabFull` errors and invoke a registered direct response completion handler.
2. Replace `crossbeam_channel::bounded(4)` and `tokio::sync::mpsc::channel(4)` in `BatchBridge` with `crossbeam_channel::unbounded()` and `tokio::sync::mpsc::unbounded_channel()`, removing blocking `resp_tx.blocking_send` in favor of lock-free `unbounded_channel::UnboundedSender::send` and adding an optional registered direct completion callback `ResponseSink = Arc<dyn Fn(BridgeResponse) + Send + Sync>` on `BatchBridge` so embedded responses complete `InFlightRequests` directly on submission without a Tokio reader task hop.
3. Update `BridgeResponse` in `src/rs/vertebra-core/src/bridge.rs` to hold `pub request_id: u64`, `pub status: u16`, `pub headers_raw: Bytes`, and `pub body: Bytes` (offering an iterator helper via `iter_raw_headers(&self.headers_raw)`), eliminating per-response `Vec<(Vec<u8>, Vec<u8>)>` allocations in `InProcessTransport::submit_response_raw`.
4. Extend `BatchSnapshot` (`Backing` enum in `src/rs/vertebra-core/src/bridge.rs`) with an `InProcess(Vec<InProcessRequest>)` variant holding zero-copy `Bytes` fields (`method`, `path`, `query`, `headers_raw`, `body`, `request_id`, `handler_id`, `path_params_raw`) and add `BatchBridge::submit_inprocess_batch(&self, requests: Vec<InProcessRequest>) -> Result<(), BridgeError>` with zero `Mutex` locking and zero `1 MiB` slab limit, while also teaching `BatchWriter::push_request` to auto-flush/seal on `SlabFull`/`ArenaFull` for legacy slab callers.
5. Update `InProcessTransport` in `src/rs/vertebra-core/src/transport/mod.rs` to pass `headers_raw: Bytes` and `body: Bytes` directly into `BridgeResponse`.
