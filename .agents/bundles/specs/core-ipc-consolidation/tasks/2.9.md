# 2.9 Storage crate fixes and dedupe

## Objective
Fix `vertebra-storage` signing pyfunctions so omitted `timestamp` arguments default to `Utc::now().timestamp()` instead of `1700000000` (Nov 2023) (`CORE-37`), deduplicate `constant_time_eq` and `sha256_hex` into `vertebra_core::util` and bound `STORAGE_RUNTIME` worker threads (`CORE-36`), and replace the 14 hand-written sync/async `NativeObjectStore` method pairs and `PyBytes` copy in `vertebra-storage/src/lib.rs` with a `storage_method!` macro and zero-copy `Bytes::from_owner` while splitting R2 chunking into `r2.rs` (`CORE-38`).

## Context
- `src/rs/vertebra-storage/src/lib.rs:447,479,534,570,610` sets `#[pyo3(signature = (..., timestamp=1700000000))]` on `sign_hmac_sha256`, `sign_s3_v4`, `sign_gcs_v4`, `sign_oci_request`, and `sign_azure_sas`, causing callers that omit `timestamp` to generate signatures expired in November 2023 (`CORE-37`).
- `constant_time_eq` and `sha256_hex` are duplicated across `vertebra-storage/src/signing.rs:15-27,416-429`, `vertebra-http/src/profile.rs:16`, and `vertebra-http/src/tls.rs:242`, and `STORAGE_RUNTIME` (`vertebra-storage/src/store.rs:21-40`) spawns a full default-sized multi-thread Tokio pool alongside `vertebra-py` (`CORE-36`).
- `NativeObjectStore` (`vertebra-storage/src/lib.rs:240-444`) hand-writes 14 sync + `_async` method pairs and copies `PyBytes` payloads via `Bytes::copy_from_slice` (`:43-45`), and R2 multipart helpers (`chunk_uniform_parts`, `R2_UNIFORM_PART_SIZE`) live inside `oci.rs` (`CORE-38`).
- `regression_tdd` applies because calling any signing function without `timestamp` currently produces a stale 2023 timestamp (`1700000000`).

- [x] 2.
